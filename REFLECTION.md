# Reflection (200–300 words)

The main challenge in the refactor wasn't choosing techniques — sharding, replication, and denormalization are well-known names — but picking the *right shard key* for each collection instead of a convenient one. My first instinct was to shard `orders` by `userId`, since that mirrors the most common query (a customer's order history). Working through the throughput requirement more carefully showed that was a trap: any unusually active account would overload a single shard, which defeats the entire point of sharding under a "thousands of transactions per second" load. Switching to a hashed `_id` fixed the write-distribution problem but introduced a real cost — "all of this customer's orders" is no longer a single-shard query — which I had to explicitly accept and document rather than pretend away.

The new requirements changed the design in a more fundamental way than I expected: they forced a split between the transactional path and the analytical path. In the initial design, I hadn't thought about analytics at all, and my first draft of the refactor ran aggregations directly against the live `orders` collection. That would have meant every dashboard query competing with checkout traffic for the same database capacity — the opposite of what "high availability" means in practice. Introducing the denormalized `salesSummary` collection, written asynchronously, was the fix, and it's the clearest example in this exercise of trading strict consistency for both availability and performance, which is the actual trade-off NoSQL design is about.

Writing the schemas as real JSON Schema files and validating documents against them, rather than just describing the design in prose, caught a real bug: my first draft of the `order` schema didn't reject an empty `items` array, which would have let an invalid order pass silently.
